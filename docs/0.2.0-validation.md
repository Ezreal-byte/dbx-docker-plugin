## 本机 Docker 实测

实际环境：Windows Docker Desktop，Docker Engine **29.7.2**，API **1.55**，Linux 容器。

使用 `127.0.0.1:2375` 和 `//./pipe/docker_engine`，两个独立 sidecar 模拟桌面与外部 MCP。临时连接与测试资源使用唯一 `dbx-v020-*` 前缀，未修改已安装 DBX 的权限文件，未执行全局清理。

- 默认关闭时调用被拒绝；查询授权、修改授权与外部 sidecar 撤回授权生效。
- 创建卷、网络及 Alpine 容器并启动；查询健康、有限日志、指标、镜像详情和历史。
- 查询卷引用、网络端点；连接与断开网络；拒绝只读写操作和删除在用卷。
- 容器 Inspect 的工具结果不包含测试环境变量中的敏感值。
- 容器状态改变后旧删除令牌被拒绝；重新预览后逐项删除容器、网络和卷成功；令牌重放被拒绝。
- Compose 预览、后台部署任务及持久化任务结果通过。
- 原有 **27 项** sidecar 兼容检查通过，涵盖连接、容器/镜像/网络/卷列表、日志流、终端二进制通道、文件上传下载、只读保护、镜像标签/历史、容器重命名、磁盘用量与清理预览。全局清理测试明确禁用。

## 复现命令

需安装项目依赖与 Go 工具链，在插件目录执行：

```powershell
go -C backend test ./... -count=1
go -C backend vet ./...
go -C backend/sdk test ./... -count=1
npm test
node scripts/check-dbx-connection-contract.mjs E:\xynanan\dbx 0db01f7f284ec6b0b090fe7369de7d05c37b25b0
npm run package
go -C backend build -o ../dist/verify-sidecar.exe .
node scripts/check-automation-sidecar.mjs dist/verify-sidecar.exe
```

真实引擎复现需要本机 TCP 2375、默认 Windows Docker 管道及已有 `alpine:latest` 镜像：

```powershell
node scripts/check-live-automation.mjs dist/verify-sidecar.exe --compat
```

脚本创建临时资源并在结束时清理。若进程被强制终止，应按输出的唯一前缀检查残留，不执行全局 prune。`dbx-plugin package` 在独立暂存目录构建，不更新 `.dbx-dev/bin`；不要用该开发缓存判断安装包版本。校验交付二进制时，从 `.dbxp` ZIP 的 `bin/windows-x64/dbx-docker-plugin.exe` 提取后将路径传给上述脚本。

## 仍需用户在 DBX 中验证

1. 安装验证包，确认连接表单和已有连接正常，Windows 命名管道可以替代 2375。
2. 打开目标连接，在右上角开启 AI/MCP 查询权限，再启用 DBX 自身的插件 AI 工具；让内置 AI 查询容器、有限日志、网络端点及卷引用。
3. 在 DBX MCP 白名单中授权测试连接，用外部客户端选择 `dbx_connection` 并查询；关闭插件权限后再次调用应失败。
4. 按需授权测试连接的写工具，验证宿主写操作确认、只读限制与插件预览流程。
5. 有远端环境时验证实际 TLS、SSH Socket、Unix Socket 和已打开桌面隧道；关闭隧道后外部调用应提示打开工作台，不应回退直连。

卷容量依赖引擎 `system/df` 的返回值，无法取得时明确显示未知。Compose 仍为显式校验的有限子集，详见 [功能路线图](ROADMAP.md)；完整 Compose、数据备份和构建不属于本次交付。权限、工具参数和任务限制见 [AI/MCP 说明](AI-MCP.md)。
